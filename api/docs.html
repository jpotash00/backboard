Install & integrate Offboard

Offboard is a drop-in web SDK that renders an AI exit-interview modal inside your cancel flow, runs a short interview, and hands your app a structured outcome — the real churn reason plus any save offer it authorized. Wiring it up is one import and one call.

Compatibility. The widget is a web SDK — JavaScript/TypeScript, running in the browser. The framework-free core works with vanilla JS, React (dedicated hook), Next.js, Vue, Svelte, or Angular. The only backend work is signing an identity token, which is a short HMAC-SHA256 function — so your backend can be any language (Python, Node, Java, Go, Ruby, PHP, C#, C++, Rust). See Verify identity.

1Install

The SDK is published to npm as offboard. It ships ESM with TypeScript types; the core import is framework-free.

$ npm install offboard

2Get your keys

Set up a tenant to generate two keys instantly — no account, no waiting:

  • public_key (pk_…) — safe to ship in your frontend. It identifies your tenant to Offboard.
  • signing_secret (ss_…) — backend only. It signs the identity tokens that authorize paid save offers. Shown once at setup — store it now.
Onboarding also captures your product context, pricing, and the save offers you're willing to make. Offboard only ever proposes offers you configured — it never invents a discount on its own.

3Quick start

Initialize once at startup, then open the flow behind your “Cancel subscription” button. The SDK renders the conversation and the authorized offer; you just react to the user's choice.

cancel-button.js 
import Offboard from "offboard";

// Once, at startup.
Offboard.init({ publicKey: "pk_live_…" });

// When the user clicks "Cancel subscription":
cancelButton.addEventListener("click", () => {
  Offboard.showCancelFlow({
    userId: "user_123",
    // Optional context — the richer it is, the sharper the diagnosis.
    context: {
      plan: "Starter", mrr: 49, tenure_days: 210,
      logins_last_30d: 27, activated: true,
      usage_summary: "Daily active; hitting the event cap.",
    },
    onAccept: (outcome) => applyOffer(outcome),      // they took the save
    onCancel: (outcome) => completeCancellation(),   // let them go
  });
});
Offboard never charges or credits anyone. On onAccept you apply the offer yourself (e.g. in Stripe) using outcome.intervention.id — the SDK only relays the decision.

4React

offboard/react exposes a hook. react is an optional peer dependency — the core import stays framework-free.

CancelButton.jsx 
import { useOffboardCancelFlow } from "offboard/react";

function CancelButton({ user }) {
  const cancel = useOffboardCancelFlow({
    publicKey: "pk_live_…",              // or call Offboard.init() once elsewhere
    userId: user.id,
    identityToken: user.offboardToken,   // required for paid offers
    onAccept: (o) => applyOffer(o),
    onCancel: () => completeCancellation(),
  });
  return <button onClick={cancel}>Cancel subscription</button>;
}

Handle the outcome

Both onAccept and onCancel receive the same Outcome object. Read the decision from it rather than re-deriving it yourself.

FieldMeaning
reasonThe real diagnosed churn reason (e.g. price_value_mismatch, never_activated), not a self-reported checkbox.
intervention.idThe authorized offer accepted (or null if none was offered).
intervention.paramsA handle to the offer's object in your billing system, e.g. { stripe_coupon: "off50_3mo" }, so you apply it without parsing text. Empty when the offer defines none.
intervention.type · .descriptionThe kind of offer (discount, pause, downgrade, …) and its human label.
mode"act" (safe to auto-apply) or "suggest" (route to a human first).
confidenceHow confident the diagnosis is.

There's also an optional onResolved(outcome) callback that fires when the interview concludes, handy for analytics.

Apply the save, then close the loop

onAccept fires when the customer takes the offer. Because Offboard only ever picks an offer you authorized, the matching object already lives in your billing system. intervention.params is your handle to it, so applying the save is a lookup, not a rebuild.

on-accept.js 
onAccept: (outcome) => {
  const { intervention } = outcome;   // { id, type, params, ... }
  // The offer already exists in your billing system; params points at it,
  // e.g. { stripe_coupon: "off50_3mo" }. Apply it from YOUR backend
  // (never call Stripe with a secret key from the browser):
  fetch("/api/apply-save", {
    method: "POST",
    body: JSON.stringify({ userId, intervention }),
  });
}
Offboard already recorded the acceptance for you. That accepted signal is the label your retention data is built on, so there's nothing extra to log here.

Close the loop with retention

Acceptance is not retention. Someone can take 50% off and still churn in month four. To learn whether a save actually held, report the outcome later from your backend (say, 90 days after the save):

report-retention · YOUR backend 
POST https://offboard.fly.dev/outcomes
Authorization: Bearer pk_live_…
Content-Type: application/json

{
  "user_id": "user_123",
  "active": true,
  "observed_at": "2026-10-08T00:00:00Z"
}

Offboard joins it back to the session and reason, so your dashboard reflects saves that held, not just offers accepted. Fire it on a schedule for every customer you saved.

Sending context

The interview is only as sharp as what it knows about the customer. Feed it real behavioral data pulled from your product analytics (PostHog, Amplitude, …) or your own database when the cancel modal opens, not a hand-written blurb. This is what separates a real diagnosis from a guess: someone who says "too expensive" but never activated doesn't have a price problem, and only your usage data can tell those two apart.

The field that carries it is signals, an open key/value map. Drop in whatever you have, named however you like, when the flow opens:

cancel-button.js 
// Pull live signals from your analytics or DB the moment the user hits cancel.
const signals = await getUsageSignals(user.id);
// e.g. { activated: true, core_feature_uses_30d: 2, seat_limit_hits: 4, onboarding: "stalled_step_2" }

Offboard.showCancelFlow({
  userId: user.id,
  identityToken: user.offboardToken,   // sign anything that gates an offer (see below)
  context: { plan: "Growth", mrr: 199, tenure_days: 210, signals },
  onAccept, onCancel,
});

Every field is optional. The typed ones are shortcuts for the signals that matter most:

signalsThe primary field. An open key/value map of live behavioral data, feature usage, limits hit, onboarding progress. The richer this is, the sharper the diagnosis.
activatedWhether they ever reached real adoption, the single most useful flag.
logins_last_30dRecent activity, a fast engagement read.
plan · mrr · tenure_daysWho they are commercially.
usage_summaryOptional free-text digest, only if you'd rather write a sentence than pass structured signals.
Trust boundary. Browser context is a convenience and is treated as untrusted; with a signing secret it's ignored in favor of the signed identity token. So signals that only color the conversation can ride in the browser context, but anything that should gate a paid offer, or that a user must not be able to forge, your backend pulls and signs into the token.

Verify identity required for paid offers

The cancel flow runs in the browser, so anything the browser sends can be forged. If a user opens devtools and posts mrr: 99999, they must not unlock your richest offer. So when your key has a signing secret, paid offers are authorized only from a token your backend signs — the context you pass from the browser is treated as untrusted.

  1. Your server signs the user's real economics with your signing_secret (never expose it to the browser).
  2. Hand the token to your frontend and pass it as identityToken. Offboard verifies the signature and authorizes the offer from the signed values.

The token is base64url(payload) + "." + base64url(HMAC_SHA256(secret, payload)), where payload is JSON of the user fields plus iat (issued-at, unix seconds). Tokens expire after 10 minutes. Any language can mint it:

sign-token.js — runs on YOUR backend 
import { createHmac } from "node:crypto";

const b64url = (b) => Buffer.from(b).toString("base64url");

export function signIdentity(secret, claims) {
  const payload = JSON.stringify({
    ...claims,                          // user_id, plan, mrr, tenure_days, activated…
    iat: Math.floor(Date.now() / 1000), // expires 10 min later
  });
  const sig = createHmac("sha256", secret).update(payload).digest();
  return `${b64url(payload)}.${b64url(sig)}`;
}
Keys without a signing secret trust the request body as-is — fine for local development, but never ship a production cancel flow on an unsecured key.

Match your look

The widget renders a neutral, theme-aware (light/dark) surface by default. Pass a theme to make it look like your product. Colours are raw HSL triples — "222 47% 11%", not #hex.

theme.js 
Offboard.showCancelFlow({
  userId: "user_123",
  theme: {
    adoptHostTokens: true,   // inherit your shadcn/ui CSS vars — colours + radius, both modes
    accent: "222 47% 11%",   // …or just a brand accent (primary CTA + send button)
  },
  // …callbacks
});

Precedence: explicit tokens (accent, primary, background, radius, …) > adoptHostTokens > the built-in neutral default. Button and offer copy are overridable too: justCancelLabel, acceptLabel, declineLabel, offerEyebrow.

Design guarantees

The SDK enforces these so a cancel flow can never trap or mislead a user:

  • The “Just cancel” escape hatch is always rendered. Someone who chooses to answer is telling the truth; someone cornered types anything to escape.
  • The conversation is short and bounded. It stays a brief exchange and closes itself — it never turns into an interrogation.
  • Offers are authorized server-side, never in the browser. The SDK only relays the decision, so a user can't unlock a save offer from devtools.
  • Transport failures never trap the user. On error the modal degrades to letting them cancel — it does not loop.

Common errors

The SDK surfaces failures with an HTTP status and a short message. The ones you'll actually hit, and what to do about each:

Paid offers require a valid token. When your key has a signing secret, a session with no identityToken — or one older than 10 minutes — is rejected with 401 rather than granting a paid offer. Sign the token on your backend at click-time; see Verify identity.
StatusCauseFix
401 invalid public keyKey is missing, mistyped, or the tenant was removed.Call Offboard.init() with the pk_… from onboarding before opening the flow.
401 requires a signed identity_tokenKey has a signing secret but no token was sent.Mint one on your backend and pass it as identityToken.
401 token expired / bad signatureToken older than 10 min, or signed with the wrong secret.Sign at click-time with the current signing_secret — never cache it.
403 origin not allowedThe page's origin isn't in your allowlist.Add it to your allowed origins during onboarding.
404 session not foundThe session is unknown or expired mid-flow.Start a fresh flow; don't reuse a session across page loads.
429 rate limit exceededToo many attempts from one key or IP.Back off for the Retry-After seconds; a normal cancel flow won't trip this.
502 temporary errorA transient upstream failure.The modal auto-degrades to letting the user cancel — no one is trapped — so just retry.
